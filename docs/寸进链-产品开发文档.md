# 第一章 产品概述

## 1.1 产品背景

"日拱一卒，功不唐捐"。打卡类产品用"每日小任务 + 积分反馈"帮助用户坚持长期目标，市面上已有大量同类应用。但这类产品有一个共同的信任短板：**积分和成就完全由平台自己记账**。

具体表现为三个问题：

一是**数字可以被悄悄改**。积分余额通常是一行数据库记录，运营侧执行一条 SQL 就能改变任意用户的余额，用户端看到的数字随之变化，但没有任何痕迹说明它曾经是多少。

二是**成就无法对外证明**。用户把徽章截图发给朋友或写进简历，接收方无从判断真伪。即便平台提供查询接口，接口的返回值同样由平台控制，第三方仍然是在信任平台。

三是**规则调整不可追溯**。签到给多少分、全清奖励多少分属于运营配置，调整后既有的历史数据按哪一版规则计算、调整本身有没有经过公示，往往不留证据。

寸进链试图解决的问题是：**让用户和第三方在不信任平台的前提下，验证积分与成就的真实性。**

## 1.2 产品定位与差异化

寸进链不是"再做一个打卡应用"，而是**一个把打卡激励做成可验证系统的技术样品**。它与普通打卡工具的核心差别在三点：

| 维度 | 普通打卡应用 | 寸进链 |
| --- | --- | --- |
| 积分记账 | 平台数据库单点记账 | 业务库 + 链上交易双账，可三方对账 |
| 成就凭证 | 截图 / 平台内展示 | 携带 Merkle 证明的链上凭证，可生成验真链接与二维码 |
| 验真方式 | 信任平台接口 | 浏览器本地重算 Merkle 根，结论不依赖服务端 |
| 规则变更 | 直接改配置 | 版本化留存 + 链上存证 + 审计日志 |
| 数据篡改 | 难以发现 | 可检测并定位到首个出错区块高度 |

一句话概括差异化：**别人存的是数据，寸进链存的是"这份数据没被动过"的证明。**

## 1.3 目标用户与使用场景

**主要用户是学习者。** 典型场景：小李在准备考研，用寸进链把"每天背 50 个单词、数学 2 小时、英语阅读 2 篇"设为长期目标，系统按天生成具体任务。他每天签到、逐项勾选，积分随之累积。坚持 30 天后他铸造了一枚"月度坚持"徽章，把验真链接发到学习小组里——组员点开链接，浏览器当场算出 Merkle 根并与区块头比对，确认这枚徽章确实在某天被记录到链上，而不是 P 图。

**次要用户是平台运营。** 典型场景：运营发现某账号在凌晨 3 点密集产生积分动作，风控中心已自动生成工单并附上证据（时间间隔、动作次数）。运营在工单里核实后判定为刷分，执行处置并回滚相应积分，整个过程写入审计日志。

**第三类使用者是任何人**（链浏览器访客、凭证核验方）。他们不需要注册，可以直接浏览区块与交易、执行全链校验，或在验真页核验一张凭证。

## 1.4 产品范围

**本期实现（v1.0）**：

- 学习者端：注册登录、目标设定、每日签到、任务勾选与日结、数据看板、积分明细、徽章墙与铸造、积分商城与兑换、目标押注、公益捐赠、自习室与排行榜

- 链浏览器：链概览、区块、交易、地址、全链校验、篡改实验室
- 凭证验真页：免登录四步验真、Merkle 本地重算、撤销展示
- 区块链内核：交易签名、Merkle 树、工作量证明、交易池批量出块、链校验与篡改定位
- 配套工具：建库脚本、种子数据生成器、链内核单元测试、前端静态检查、端到端验收脚本、配图渲染器、文档导出脚本

**本期不做**：

- 真实资金充值、提现与积分交易（积分仅平台内使用，不具备货币属性）
- 多节点分布式部署与节点间共识（采用单节点，工作量证明用于提高篡改成本）
- 移动原生 App（本期为响应式 Web）
- 第三方账号登录、消息推送

## 2.3 用户故事与验收标准

**故事一：签到**

> 作为学习者，我希望每天签到能拿到积分，并且连续天数越多拿得越多，这样我有动力不断签。

验收标准：

1. 今日未签到时，签到按钮可点击；点击后余额立即增加，并弹出提示说明本次获得多少分、当前连续多少天。
2. 今日已签到时，再次签到返回明确的错误提示，余额不变。
3. 连续天数按"昨天签过则累加、否则重置为 1"计算。
4. 每次签到都产生一笔链上交易，积分明细中能看到对应的交易号。

**故事二：验真**

> 作为收到凭证的第三方，我希望不注册、不安装任何东西就能确认这张凭证是真的，而不是平台说了算。

验收标准：

1. 验真页无需登录即可访问。
2. 输入有效凭证号，页面展示"凭证有效"，并逐条列出四步校验的结果。
3. 页面展开显示 Merkle 路径，并说明浏览器是如何自己算出根的。
4. 输入有效但已撤销的凭证号，页面展示"凭证已撤销"+撤销理由，同时展示"链上交易仍然存在且 Merkle 证明通过"。
5. 输入伪造或抄错的凭证号，页面给出"查不到"而不是"无效"这种含糊结论。

**故事三：篡改**

> 作为怀疑数据被改过的用户，我想亲手改一笔数据看看系统能不能发现。

验收标准：

1. 篡改实验室列出至少六种篡改方式，每种都说明改什么、预期会被哪一层检测到。
2. 选择一种篡改并执行后，页面展示"改了什么、改成什么、动手前后的校验结果"。
3. 篡改后校验必须失败，并指出首个出错的区块高度。
4. 实验只在内存副本上进行，数据库不受影响，可反复执行。

# 第三章 功能设计

## 3.1 积分体系设计

积分体系遵循"入口少、出口少、每笔可追溯"的原则。发放入口只有四个，消耗出口只有四个，闭环清晰。

### 3.1.1 发放入口

| 入口 | 规则 | 当前生效值 | 说明 |
| --- | --- | --- | --- |
| 每日签到 | 固定基础分 | 6 分 | 每天一次 |
| 连续加成 | 阶梯额外分 | 1,2,3,5,8,12,18,25,40 | 连续第 n 天的额外分 |
| 任务完成 | 每个任务固定分 | 1 分 | 撤销完成会同步扣回 |
| 当日全清 | 额外奖励 | 13 分 | 每日只触发一次 |

选择阶梯而非线性叠加的原因：线性叠加会让长期坚持者的收益增长过快，造成积分通胀，最终使商城价格失去意义。阶梯设计在奖励坚持的同时控制了发行总量。

### 3.1.2 消耗出口

| 出口 | 计费 | 链上交易类型 | 说明 |
| --- | --- | --- | --- |
| 铸造徽章 | 按徽章定价 | BADGE_MINT | 徽章是链上凭证，可对外验真 |
| 商城兑换 | 商品价格 × 兑换系数 | REDEEM | 与库存扣减同一事务 |
| 目标押注 | 冻结本金，按结果结算 | STAKE / STAKE_WIN / STAKE_LOSE | 赢家的收益来自奖池，不是凭空增发 |
| 公益捐赠 | 捐赠额 + 平台 10% 配捐 | DONATE / MATCH | 配捐由铸币账户支出并留痕 |

### 3.1.3 押注结算逻辑

押注是四个出口中唯一带不确定性的功能，因此结算逻辑需要明确：

1. 发起押注时，本金从可用余额转入冻结积分，此时**不产生链上转账**（钱还没离开账户）。
2. 到期结算时，比较实际完成数与约定数量。
3. 若达成，按约定倍率从奖池账户向用户返还，返还金额**以奖池实际余额为上限**，避免超发。
4. 若未达成，冻结的本金转入奖池账户，成为后续赢家的资金来源。

这个设计使奖池的收支始终守恒：押注失败者的本金流入，押注成功者的收益流出，池子不会被掏空，也不会凭空产生积分。

## 3.2 成就凭证设计

### 3.2.1 凭证包含什么

一张凭证记录以下信息：所属用户与链上地址、徽章名称与等级、序列号（格式 `ZJ-XXXX-XXXX-XXXX`）、验真码、铸造时间、消耗积分、链上交易号、所在区块高度、Merkle 证明路径、状态（有效 / 已撤销）、撤销理由与撤销时间。

### 3.2.2 为什么凭证要在浏览器端验

如果验真结论由服务端返回，那么服务端自己就能伪造一个"有效"，验真就退化成了"相信平台"。因此系统把最关键的第四步——**根据交易号与 Merkle 路径重算根，并与区块头比对**——放在浏览器里完成。

服务端提供的是原始材料（交易号、路径、块头），浏览器负责计算。这样一来，验真结论的成立不依赖于对平台的信任。这也是区块链在这个产品里的意义所在：**不是把数据存两份，而是让"存量"这件事可被外部独立核验。**

### 3.2.3 撤销与伪造必须区分

凭证可能因为重复铸造、用户申请退回、违规发放等原因被撤销。如果撤销后凭证直接查不到，第三方就无法区分"这张凭证从来不存在（伪造）"与"这张凭证曾经存在但已被收回（撤销）"。

因此系统把两者分开处理：

- 数据库中保留凭证行，状态置为 `revoked`，并记录撤销理由与时间。
- 链上的铸造交易不动，仍然可以被 Merkle 证明验证。
- 验真页同时展示"已撤销"和"Merkle 证明通过"两个结论，并解释二者的含义。

## 3.3 风控设计

风控的目标不是把所有异常行为都拦下来，而是**把可疑行为变成可核查的工单**，交给人工判断。因此每条规则命中时都必须携带证据字段。

| 规则 | 级别 | 判定条件 | 证据字段 |
| --- | --- | --- | --- |
| 疑似秒签 | 低 | 登录后 2 秒内完成签到 | 登录与签到的时间差 |
| 同设备多账号 | 高 | 同一设备指纹被多账号使用 | 设备指纹、关联账号数 |
| 任务重复勾选 | 中 | 24 小时内同一任务勾选/取消超过 3 次 | 操作次数与时间分布 |
| 积分异常暴增 | 中 | 1 小时内入账超过 120 分 | 时段内的流水明细 |
| 深夜批量操作 | 低 | 0 至 5 点产生 5 笔以上积分动作 | 时间点分布、IP |

管理端的风控页支持按规则、级别、处理状态筛选，处置时可填写处置说明，并可勾选同时封禁账号。所有处置写入审计日志。

## 3.4 管理端信息架构

管理端采用独立外壳（侧栏 + 面包屑顶栏），共十一个页签。

| 页签 | 解决的问题 | 首屏内容 |
| --- | --- | --- |
| 概览 | 今天有什么需要我处理 | 待办列表（按优先级排序，每条可直接跳转到已排好序的列表） |
| 用户 | 谁在用、谁异常 | 用户表格，支持按状态、等级、积分排序与搜索 |
| 积分规则 | 规则现在是什么、改过几次 | 当前生效规则 + 全部历史版本 |
| 奖励商品 | 徽章和商品怎么配 | 徽章表 + 商品表，支持上下架与编辑 |
| 兑换订单 | 哪些单要发货 | 订单表，按状态筛选，支持发货与取消退分 |
| 风控 | 哪些账号可疑 | 工单列表，按级别与状态筛选，支持处置 |
| 链运维 | 链现在什么状态 | 链概览、交易池、手动出块、难度调整 |
| 对账 | 账对得上吗 | 三方口径数值 + 不平用户清单 |
| 公告 | 有什么要通知 | 公告列表，支持新增与置顶 |
| 审计日志 | 谁做了什么 | 操作记录，含操作者、动作、变更前后值 |
| 数据看板 | 整体情况如何 | 趋势、漏斗、分布、构成、活跃时段 |

**设计要点：概览页第一屏不是统计数字，而是待办事项。** 运营打开系统最想知道的是"有什么需要我做"，而不是"总共有多少用户"。每条待办都附带跳转入口，点击后落到已按该问题排好序的列表，而不是把用户丢进一张大表自己找。

## 3.5 链浏览器与篡改实验室

链浏览器面向所有人免登录开放，包含链概览、区块列表、区块详情、交易详情、地址查询、全链校验与篡改实验室。

篡改实验室是交互性最强的模块，提供六种篡改方式：

| 篡改方式 | 改什么 | 预期被哪一层检测到 |
| --- | --- | --- |
| 伪造存证时间 | 区块的时间戳 | 区块哈希变化，与记录值不符 |
| 改写区块 nonce | 区块的随机数 | 哈希不再满足难度前缀 |
| 修改交易金额 | 某笔交易的金额 | 交易号变化，Merkle 根不匹配 |
| 修改交易备注 | 某笔交易的备注 | 同上 |
| 调换块内交易顺序 | 块内两笔交易的顺序 | Merkle 根变化，与块头记录不符 |
| 重挖区块 | 重新挖矿使该块自身合法 | 下一块记录的前块哈希对不上，从该块之后整条断裂 |

实验过程：选择方式与目标 → 系统在内存中复制一份链数据 → 执行篡改 → 重新运行完整校验 → 展示"改了什么、改成什么、动手前后的校验结果、首个出错的区块高度"。整个过程不修改数据库，可反复实验。

第六种"重挖区块"是最有教学价值的一种：它先让被改动的区块自身看起来完全合法（哈希正确、难度达标），再展示整条链依然能抓住它。这比只演示"改了 nonce 就失败"更接近真实的攻击方式。

# 第四章 技术架构

## 4.1 总体架构

系统采用分层架构，自上而下分为五层。

![图 4-1 系统总体架构](figs/arch.png)

| 层次 | 职责 | 主要文件 |
| --- | --- | --- |
| 用户与访问层 | 四个端的前端页面与交互 | public/index.html、chain.html、admin.html、verify.html 及对应 JS |
| 接入与鉴权层 | 路由分发、令牌签发与校验、静态资源托管 | server.js、lib/auth.js、routes/*.js |

## 4.3 区块链内核设计

### 4.3.1 数据结构

**交易**包含：`from`（发送方地址）、`to`（接收方地址）、`amount`（金额）、`type`（交易类型）、`memo`（备注）、`nonce`（序号）、`ts`（时间戳）、`sig`（Ed25519 签名）、`txid`（交易号）。

交易号的计算方式：剔除 `sig` 字段，把剩余字段按固定顺序拼接成规范化字符串，取 SHA-256。之所以排除签名，是为了避免"签名包含交易号、交易号又依赖签名"的循环依赖。

**区块**包含：`height`、`prevHash`、`merkleRoot`、`ts`、`difficulty`、`nonce`、`miner`、`txCount`、`hash`。创世块的 `prevHash` 为全零哈希。

**交易类型**：GENESIS（创世）、CHECKIN（签到）、TASK_DONE（任务完成）、DAY_CLEAR（当日全清）、BADGE_MINT（铸造徽章）、REDEEM（商城兑换）、STAKE（押注冻结）、STAKE_WIN / STAKE_LOSE（押注结算）、DONATE（捐赠）、MATCH（平台配捐）、ADJUST（管理调整）。

![图 4-2 区块结构与 Merkle 树](figs/block-merkle.png)

### 4.3.2 出块策略

若每笔业务交易都立即出块，4 890 笔交易会产生 4 890 个区块，挖矿开销不可接受。因此引入交易池与批量打包。

业务动作产生的交易先写入 `txs` 表并把 `block_height` 置空，表示"待打包"。触发打包的条件有两个，满足其一即可：

1. **攒批触发**：业务动作完成后检查待打包笔数，达到阈值（默认 25 笔）立即出块。
2. **超时兜底**：定时器检查，若交易池非空且距上次出块超过设定间隔，则打包出块，避免低频时段交易长期悬置。

打包时按"时间戳升序、交易号升序"取出待打包交易，计算 Merkle 根，构造区块头，执行工作量证明挖矿，最后在同一事务内写入区块记录、回填交易的区块高度、更新相关账户的链上余额与交易计数。

### 4.3.3 链校验算法

校验按高度升序逐块执行四项检查：

1. **链式哈希**：重算该块哈希并与记录值比对；确认该块记录的 `prevHash` 等于上一块实际哈希。
2. **Merkle 根**：按与出块完全一致的排序取出块内交易，重算 Merkle 根并与块头比对。
3. **难度达标**：确认区块哈希满足该块声明难度对应的前缀条件。
4. **交易签名**：对块内每笔交易重新验签。

任一检查失败即中止，返回首个出错的区块高度与失败原因。返回具体高度而非仅返回"失败"，是为了让篡改实验室能够明确指出问题出在哪一块。

**关键细节：排序一致性。** 若出块按"时间戳升序、交易号升序"取交易，而校验未指定排序，当块内存在时间戳相同的交易时，数据库返回顺序可能与出块时不同，重算的 Merkle 根自然对不上，表现为"链被篡改"的误报。解决方案是让出块与校验共用同一套排序规则。这个问题在开发过程中真实出现过，只有执行完整链校验才会暴露。

### 4.3.4 密钥管理

系统的系统账户（铸币、销毁、奖池、公益）各自持有一把 Ed25519 密钥，密钥持久化在 `data/` 目录下。这样做的原因是：如果系统账户的密钥每次启动重新生成，那么重启之前产生的历史交易就无法通过验签，全链校验会失败。持久化密钥是保证"链的每一笔交易在任何时候都可验签"这一不变量的必要条件。

## 4.6 安全设计

| 风险 | 应对措施 |
| --- | --- |
| 密码泄露 | 随机盐 + SHA-256 摘要存储，盐值单独存列 |
| 会话伪造 | 令牌由服务端密钥 HMAC-SHA256 签名，含过期时间 |
| 越权操作 | 写操作的 SQL 条件中显式带上用户编号，不只依赖前端传参 |
| 管理端被越权访问 | 中间件层统一校验运营角色 |
| 数据库被直改 | 每笔交易有 Ed25519 签名，链校验逐笔验签，无法伪造 |
| 验真结论被服务端伪造 | Merkle 根重算放在浏览器端，服务端只提供原始材料 |
| 操作无法追责 | 管理端高危操作写入审计日志，记录变更前后值 |

| `tools/build-docx.js` | 把 Markdown 文档导出为 Word（含多级编号与目录域） |

**为什么要有前端静态检查脚本。** 原生 ES 模块的导入导出不匹配（例如从 A 模块导入了 B 模块里才有的函数）会导致整页静默空白——浏览器只在控制台报错，页面上没有任何可见提示，截图完全看不出异常。这个脚本在转换前扫描八个前端模块的语法、导入导出匹配情况与 HTML 引用的资源是否存在，把这类问题挡在运行之前。

**为什么验收要以断言而不是截图为准。** 页面渲染出错时会显示一张包含错误信息的提示卡，这类页面的文本长度同样可以超过阈值，仅判断"内容长度够了"会漏掉错误。因此验收脚本在断言"渲染出内容"时，同时断言"页面里没有出现异常兜底卡"。这一条断言在开发中确实抓到了一个真实缺陷：管理端数据看板页签因为一个参数类型错误而整体渲染成错误卡，仅看截图无法发现。

## 6.4 开发中修复的典型缺陷

记录几个有代表性的问题，它们都曾以"看着不像这个问题"的形式出现。

| 现象 | 真正原因 | 修复 |
| --- | --- | --- |
| 页面整片空白，截图看不出异常 | 前端模块从一个文件导入了实际定义在另一个文件的函数，ES 模块解析失败 | 修正导入来源，并编写静态检查脚本前置拦截 |
| 全链校验在高度 0 就失败 | 创世交易没有签名却被标记为验签通过 | 让创世块同样由铸币账户签名 |
| 全链校验报"Merkle 根不匹配" | 出块按时间戳与交易号排序，校验未指定排序，块内时间戳相同的交易顺序不一致 | 出块与校验共用同一套排序规则 |
| 管理端数据看板页签渲染成错误卡 | 传入的参数类型与约定不符（应为数组，实为字符串） | 修正调用点，并让接收方兼容两种类型 |
| 趋势曲线末尾掉到 0，像系统故障 | 趋势里包含了"今天"这个尚未结束的自然日 | 趋势只统计已结束的日期，并在界面上说明 |
| 每张表的数据看起来像假的 | 早期做法是直接 INSERT 造数据，导致链上交易与业务数据对不上 | 改为把真实业务逻辑跑一遍，让演示数据与真实运行走同一条代码路径 |

# 第七章 迭代规划

## 7.1 已知限制

| 限制 | 影响 | 说明 |
| --- | --- | --- |
| 单节点部署 | 工作量证明未用于节点间共识，仅提高篡改成本 | 真实抗篡改能力来自多节点各自保存副本 |
| 链上只存积分转移 | 链能证明"某时刻发生了多少分的转移"，但不能独立证明对应哪件商品 | 可把业务对象的哈希写入交易备注 |
| 交易明文可见 | 链上数据对所有人可见，存在隐私问题 | 可引入零知识证明证明属性而不暴露明细 |
| 数据线性增长 | 长期运行需要归档策略 | 可对历史区块做分层归档 |
| 无真实资金 | 积分不具备货币属性 | 引入真实权益需另行评估合规要求 |

## 7.2 后续迭代方向

**v1.1：让链能定位到业务对象。** 把成就凭证的序列号、兑换单编号等业务标识的哈希写入交易备注字段，使链上记录可以追溯到具体的业务对象，而不仅仅是金额与类型。

**v1.2：多节点与共识。** 把链扩展到多个节点，引入最长链规则与节点间同步，使篡改需要同时控制多数节点。这一步会让工作量证明真正发挥作用。

**v1.3：可嵌入的验真组件。** 提供一个轻量脚本，让第三方网站可以把验真能力嵌进自己的页面。用户出示凭证时，第三方站点在页面内即可完成验证，不需要跳转到平台。

**v1.4：真实学习数据接入。** 接入番茄钟、单词背诵、在线课程等真实数据源，降低打卡本身被作弊的空间——当前系统中"完成任务"仍由用户自行勾选，是整条信任链上最弱的一环。

**v1.5：可组合成就体系。** 支持由多个基础徽章合成更高阶凭证，使成就体系具备成长性与收集性。

## 7.3 产品价值总结

回到最初要解决的问题：**让用户和第三方在不信任平台的前提下，验证积分与成就的真实性。**

寸进链的答案是三点：**账要能对**——业务流水、账户台账与链上余额三个口径互相校验，任何一处被改动都能被发现；**凭证要能验**——验证的关键计算放在浏览器端，结论不依赖对平台的信任；**改动要能查**——规则变更版本化留痕、管理操作写审计日志、链上数据被篡改能定位到具体块高。

区块链在这个产品里不是噱头，也不是把数据存两份。它解决的是一个具体的问题：**把"这份数据没被动过"从一句承诺，变成一个任何人都能自己算出来的结论。**
